Context

The trade doesn’t wait at a desk

Much of a trade happens away from a desk: at loading points, during unloading, between calls with suppliers and transporters. The risk with operational mobile is drift — I designed FarMart PRO in parallel with FarMartOS so both products tell the same story about the same trade.

Little time, little screen

Someone on site needs the answer in seconds: what’s pending, and what can I do now?

Money moves from the field

Payment requests and adjustments start where the work happens, so they need to be clear and attributable.

One truth across devices

Whatever the phone shows has to match the OS, or trust in both products breaks.

Design questionHow might we give people on site the context and actions they need, without the phone ever disagreeing with the enterprise system?

Principles

Operational mobile isn’t a scaled-down desktop

Copying the OS onto a phone would have meant dense tables nobody can read in a warehouse. Instead, I designed PRO around four principles.

Task context first

Open on the state of the trade and what’s pending, not on every field the record holds.

Quick, permitted actions

Show only the actions the person and the trade’s state allow, one tap away.

Progressive disclosure

Totals first; the breakdown behind any number is a tap deeper.

Continuity across devices

Same names, same order, same state as the OS, so field and finance can talk about one record.

Action pattern

Every action follows the same loop

Whether someone requests a payment or records an adjustment, the interaction follows one predictable loop. Learning it once means every new action feels familiar.

Decisions

What I designed into PRO

Four decisions carried most of the weight. Each one ties the phone back to the same record people see on the OS.

  1. Order context in one place

    A single order view brings together its documents, payments and delivery details, so nobody switches apps to answer a question on a call.

  2. A separate balance for each party

    Each counterparty, and tax, has its own balance and payment flow, in the same structure as the OS, instead of one blended total.

  3. Attributed adjustments

    Payment requests and adjustments start from the phone, and every adjustment shows who raised it and why.

  4. Actions follow the trade’s state

    When a trade’s state changes on the OS, PRO reflects it, so the phone never offers an action the system will refuse.

Hard cases

What a field app has to survive

The happy path is the easy part. These are the situations an operational app has to handle gracefully. Documenting exactly how PRO handles each one is still in progress, so I list them as design considerations, not shipped behaviour.

01Slow or no networkClear state while an action is waiting to go through
02Double tapsNever create the same request twice
03Changed elsewhereThe trade moved on the OS while the phone was open
04Not allowedExplain why an action is unavailable, and who can take it
05Missing evidenceSay exactly which input or document is still needed
